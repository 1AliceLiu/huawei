# 实时车辆类别事件 API

`open_preview.bat` 启动的 `realtime_web.py` 同时提供预览、标定和车辆事件接口。所有源都从 `huawei-rtsp.txt` 读取，沿用当前模型。每路摄像头独立跟踪、独立排序。一辆车通过多个摄像头时，每路分别产生事件。

`aiserver` 已部署相同流程，服务器 HTTPS 地址、访问凭证及运维方法见 [服务器部署说明](../deploy/aiserver/README.md)。

## ROI 与过线规则

每帧使用检测框底边中点作为车辆落地点，计算方式为 `((x1 + x2) / 2, y2)`，随后按实际图像宽高归一化。使用点在多边形内的算法判断落地点是否处于 ROI，边界视作区域内。固定机位下，这个点通常比框中心更接近车辆所在路面位置。

实时事件需要满足全部条件。

1. 同一跟踪 ID 在终点线来车侧至少连续两次观测到落地点位于 ROI 内。离开来车侧 ROI 后重新累计。
2. 相邻观测的间隔最多为 0.5 秒。
3. 落点轨迹穿过用户绘制的有限终点线，交点位于 ROI 内。
4. 穿越方向与箭头规定的线两侧方向一致，且运动向量与箭头向量的点积为正。
5. 车辆从线的一侧超过 3 像素的位置，移动到另一侧超过 3 像素的位置。线旁的 3 像素带用于抑制位置抖动。

同一连续轨迹只记一次。检测框擦到 ROI、车辆逆向通过、跨过终点线延长线均不生成事件。过线之后恰好驶出 ROI 的车辆，只要过线交点有效，仍可生成事件。

ROI 应沿可见路面绘制，覆盖车辆到达终点线之前的一段路程。终点线应放在车身清晰、遮挡少且仍有空间观察过线后落点的位置。车身被遮挡或画面截断时，框底边可能偏离实际接地点，这些场景需要用现场视频核验。

## 最终类别的确定

模型仍输出逐帧类别。每路使用独立的 ByteTrack 关联车辆，关联以位置和运动为依据，类别跳变可以继续累计到同一个车辆 ID。

只使用落地点处于 ROI 内、且位于终点线来车侧的检测作为分类证据。每 200 毫秒取权重最高的一次观测，各类别累计权重，最后选择总权重最大的类别。

```text
单帧权重 = 检测置信度² × sqrt(检测框面积 / 图像面积) × 边缘系数
边缘系数 = 0.25（检测框距离任一图像边缘不超过 2 像素），否则为 1
```

时间分桶限制高帧率下重复观测的影响。面积权重增强目标较大时的证据，边缘系数降低截断框的影响。权重完全相同时，采用先累计的类别。类别在几何过线时冻结，之后的类别跳变不改写已生成事件。API 始终返回最可能类别。

该权重是工程初始方案，需要使用每路人工标注的完整过线轨迹评估。验收应分别统计漏计、重复计数、顺序错误和最终类别准确率，并将结果与单帧类别及简单多数投票对照。当前实现测试覆盖规则和接口，尚无人工真值测得的准确率。

## 接口

其他设备将下面的 `127.0.0.1` 替换为运行预览服务的机器 IP。服务默认使用现有 8000 端口，部署范围为能访问该机器的可信网络。当前 HTTP 服务无身份认证，公网接入需要在网关配置 HTTPS 和访问控制。

### 查询摄像头状态

```http
GET http://127.0.0.1:8000/api/traffic/cameras
```

响应的 `cameras` 数组包含每路的 `camera_id`、`camera_name`、`status`、`last_frame_age_s`、`tracking_resets` 和 `pending_events`。`camera_id` 沿用源和裁剪配置的稳定标识，源列表重排不会改变它。

| status | 含义 |
| --- | --- |
| active | 已处理该路有效标定下的视频帧 |
| needs_calibration | 尚未保存完整 ROI、终点线和方向 |
| waiting_for_frame | 等待首帧 |
| stream_stale | 最后处理帧的接收时间已超过 2 秒 |
| frame_size_mismatch | 当前画面宽高比与标定不匹配 |
| calibration_error | 标定文件读取失败或数据无效 |

### 增量读取车辆事件

```http
GET http://127.0.0.1:8000/api/traffic/events?after=0&limit=100
```

示例响应如下。类别编号与当前模型的 `names` 一致。

```json
{
  "events": [
    {
      "event_id": 101,
      "camera_id": "40b362ef7d99a8085234a33c42b69e702318c280b70eb3821ddfc9f1f58cd0d7",
      "camera_name": "dahua1003240",
      "sequence": 23,
      "crossed_at": "2026-11-24T03:20:12.340+00:00",
      "class_id": 8,
      "class_name": "Private Car"
    }
  ],
  "next_after": 101,
  "has_more": false
}
```

| 字段或参数 | 契约 |
| --- | --- |
| after | 只取 `event_id > after` 的事件，默认 0 |
| limit | 每次返回 1 至 1000 条，默认 100 |
| camera_id | 可选，从摄像头状态接口取得，用于只读取一路 |
| event_id | 全局递增的入库编号，供游标和消费端去重使用 |
| sequence | 同一摄像头按过线时间排列的递增序号 |
| crossed_at | 根据相邻落点插值得到的 UTC 过线时间，采用本机解码收帧时钟 |
| next_after | 下一次请求使用的游标，空结果时保持原游标 |
| has_more | 当前页后仍有事件可读 |

接收方先处理成功当前页，再保存 `next_after`。`has_more=true` 时立即读取下一页，否则可每 0.5 秒轮询一次。重试相同游标会再次返回尚未越过游标的事件，接收方用 `event_id` 去重。更换摄像头筛选条件时，应分别保存游标。

同一摄像头按插值过线时间排序。同一毫秒的事件以内部跟踪 ID 打破平局。通常额外等待约 0.5 秒发布，以处理同帧多车和线旁防抖确认的顺序。如果更早的车辆仍停留在线旁防抖带内，后续事件等待它确认、退回或跟踪失效。`pending_events` 可用于观察等待数量。跨摄像头的 `event_id` 代表入库顺序，各摄像头的网络延迟可能不同。

无效参数返回 HTTP 400，未知摄像头或路径返回 404，事件服务或存储不可用返回 503。错误体统一为 `{"error": "说明"}`。所有接口响应均为 JSON，并禁止缓存。

## 存储与运行边界

事件保存在 `output/traffic_events.sqlite3`，采用事务写入。服务重启后已入库事件和序号继续保留。备份应使用 SQLite 备份机制，或者在服务停止后复制数据库及其 WAL 文件。

断流、重连、两次检测帧的接收时间间隔超过 0.5 秒、画面尺寸变化或标定修改时，该路重新建立跟踪。已确认但待排序发布的事件会在重置时保存。中断期间穿线的车辆可能漏计，严重遮挡或 ID 切换可能漏计或重复计数。进程被强制结束时，尚未入库的缓冲事件也可能丢失。

本机收帧时间包含上游缓冲和网络延迟。应先恢复视频连续性，再用人工标注核验顺序和类别。程序保留最新帧以控制延迟，低检测帧率也会导致过线证据不足。

2026-11-24 接入时已有完整标定的摄像头为 `dahua1003240`、`dahua1003241`、`dahua1003246`、`dahua1003294`、`dahua1003295`。`dahua1003242`、`dahua1003243`、`dahua1003252`、`dahua1003292`、`dahua1003293` 需要补齐标定。完整标定通过原有页面保存后自动生效。

模型类别为 `Coach`、`Franchised Bus`、`HGV`、`LGV`、`Light Bus`、`MGV`、`Motorcycle`、`PLB GMB`、`Private Car`、`Taxi`、`Van`、`Container`，编号依次为 0 至 11。
